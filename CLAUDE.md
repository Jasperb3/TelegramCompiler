# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Python environment

> **IMPORTANT: Always install packages into `.venv` — never system-wide.**

A virtual environment lives at `.venv/`. Activate it before running any Python command:

```bash
source .venv/bin/activate
```

To set up from scratch:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
```

```bash
# Run all tests
pytest

# Run a single test file
pytest tests/test_db.py -v

# Run a single test

# Run the CLI (requires config.yaml)
python -m tg_compiler.main --batch
python -m tg_compiler.main --batch --since 00:00        # re-scrape from midnight UTC today

python -m tg_compiler.main --daemon

python -m tg_compiler.main --analyse --since 2026-06-07 # prepend front page for a specific date
```

## Architecture

The pipeline runs in five sequential stages, each in its own module, sharing `db.py` as storage:

```
Telegram (Telethon) → scraper.py → db.py ← analyzer.py (LM Studio) → triage.py → generator.py
                                                                                        ↓
                                                              briefings/YYYY-MM-DD/TheDailyTelegram_YYYY-MM-DD_HHMMSS.pdf
                                                                                        ↓
                                                                          synthesiser.py (LM Studio)
                                                                                        ↓
                                                                   intelligence front page prepended to PDF
```

**`config.py`** — Single `AppConfig` Pydantic model loaded from `config.yaml`. Use `load_config(path, env_override=True)` everywhere; it reads `TG_API_ID` / `TG_API_HASH` / `LM_API_TOKEN` from env (`.env` is auto-loaded by `main.py` via `python-dotenv`). Every config model (including all nested sub-models) has `extra="forbid"` so YAML typos fail loudly at any nesting level. All fields in the config model are actively used — see `config.yaml.example` for the full reference with comments. `StorageConfig.analysis_lookback_days` (optional, defaults to `retention_days`) is the **analysis window**: `analysis_lookback_days_effective()` / `analysis_cutoff(now)` are the single place that fallback lives, and `main.py` uses them both to scope `--batch`'s analysis queue and to cap `telegram.lookback_seconds`. Past `retention_days` the media a post references has already been deleted by `purge_old_media()`, so analysing it means analysing it blind on its text — setting the field higher only buys text-only analyses. `ChannelConfig.credibility` (default `1.0`) is a per-channel credibility prior multiplied into the composite score alongside `priority`. `TriageConfig.rumor_penalty` (default `0.7`) down-weights posts with `category == "Rumor"`. `TriageConfig.dedup_jaccard_threshold` / `dedup_entity_overlap_count` / `dedup_entity_cluster_overlap_count` (defaults `0.28`/`3`/`4`) configure `triage._find_duplicate()`'s dedup thresholds. `AppConfig.channel_priority_map()` / `channel_credibility_map()` / `channel_link_map()` build the slug-keyed dicts `main.py` and `synthesiser.py` both need, so the three dict comprehensions can't drift out of sync between callers. `AnalysisProfile` + `LMStudioConfig.analysis_profiles` hold **per-run-mode analysis settings**: `--batch`/`--since` resolve the `batch` profile, `--daemon` the `daemon` one, and `--analysis-profile NAME` overrides either. A profile carries the model **and** the settings that must travel with it (token budgets, concurrency, context length, batch sizes) because those are model-specific — a reasoning model truncates below `analysis_base_tokens: 9500`, while several large-budget image requests at once exhaust LM Studio's context. Every profile field is optional and only non-`None` values override. `with_analysis_profile()` (on both `LMStudioConfig` and `AppConfig`) **re-constructs** the model rather than using `model_copy(update=...)`, which skips validators — a profile could otherwise set `analysis_base_tokens` above `analysis_max_tokens` and silently truncate every response; a profile's `model` maps onto `analysis_model`, leaving `model` as the global fallback synthesis resolves through. `main()` resolves the profile **once** and hands the resolved `AppConfig` to `run_batch`/`run_daemon`, so budgets, batch sizes, concurrency, the model key and `model_used` provenance all follow with no further plumbing. An explicitly named missing profile is a `SystemExit`; a missing *mode default* falls back to the unprofiled config, so configs predating this feature are unaffected.

**`db.py`** — Owns the SQLite schema and all SQL. The two domain dataclasses (`PostRecord`, `AnalysisRecord`) live here. `AnalysisRecord` includes `title` (LLM-generated 5-10 word headline) and `threat_level` (one of `CRITICAL`, `HIGH`, `MODERATE`, `LOW`). `insert_post(post, commit=True)` returns `None` on duplicate (UNIQUE on `channel_id + message_id`) — callers use this to skip already-seen posts; `commit=False` lets a caller batch several inserts under one transaction (see `scraper.py`), flushed later via `Database.commit()`. `get_unanalysed_posts(since=None, limit=None)` drives the analyzer's work queue; when `since` is given it adds `p.timestamp >= ?` (same lexicographic ISO-8601-string comparison as the range helpers below) so a scoped `--since` run doesn't sweep up the full historical backlog of stuck unanalysed posts. It orders `p.timestamp ASC` and honours `limit`, so a large historical backlog can be drained oldest-first in bounded chunks instead of being pulled into memory whole. `count_unanalysed_posts(since=None)` is the `SELECT COUNT(*)` companion, sharing the same join and `since` clause — `process_unanalysed()` uses it for its exclusion-count log line, which previously materialised the entire backlog as `PostRecord` objects on every daemon sweep. `update_post_media_paths(post_id, paths)` rewrites a post's paths after `scraper.repair_missing_media()` recovers files, so the repair isn't retried every run. `reset_all_cursors()` sets every channel cursor to 0 (used by `--since`). Safe migrations run at `init_schema()` time using `PRAGMA table_info` before any `ALTER TABLE` — safe on both fresh and existing databases. `get_days_posts_with_analyses()` and `get_posts_with_analyses_in_range(start_date_str, end_date_str)` both build `(PostRecord, AnalysisRecord)` pairs via the shared `_rows_to_pairs()` helper; both compare `p.timestamp` against Python-computed `[start, end)` date bounds (lexicographic on the uniform ISO-8601 UTC timestamp strings) rather than `DATE(p.timestamp) = ?`, so `idx_posts_timestamp` is used via `SEARCH` instead of a full table `SCAN`. The `intel_assessments` table (`date` PK, `intel_json`) persists each day's synthesised intelligence JSON via `save_intel_assessment(date_str, intel)` (upsert) / `get_intel_assessment(date_str)` (returns `None` if absent), feeding next-day continuity in `synthesiser.py`. `init_schema()` also creates `idx_analyses_post_id` and `idx_posts_timestamp` indexes; `__init__` enables `PRAGMA foreign_keys=ON` and (for non-`:memory:` paths) chmods the DB file to `0600` via `secure_file()`. `Database` supports `close()` and use as a context manager (`__enter__`/`__exit__`).

**`scraper.py`** — Telethon async context manager. `build_post_record(client, msg, channel_id, channel_cfg, storage_cfg)` is the single module-level coroutine that turns a Telethon message into a `PostRecord`: downloads a photo (one retry, cleaning up any partial file on permanent failure), normalises the timestamp to aware UTC, and sets `has_video`/`has_images`/`raw_json` (`{"id", "text"}`). Both `Scraper.scrape_channel()`'s loop and `main.run_daemon()`'s live message handler call it, so the two paths can't drift out of sync again (they already had once, on `raw_json`). `Scraper.scrape_channel()` fetches messages since the last cursor (`offset_id=last_seen_id`); when the cursor is 0 (first run or after reset), uses `offset_date = now - lookback_seconds` instead. `iter_messages` is called with `limit=None` — no artificial cap, so a long backlog (e.g. after `--since`) is fully drained in one run, and with `reverse=True` so it walks oldest-to-newest from the cursor — `max_id_seen` then only ever advances monotonically, so a mid-iteration crash's cursor write covers exactly the messages already inserted. Skips `MessageService` objects (system events), inserts to DB, and advances the per-channel cursor. Posts are inserted with `commit=False` and flushed in one `db.commit()` per channel (in the `finally` block, alongside the cursor write, or standalone if the cursor didn't move) instead of one commit per row — a mid-channel crash loses at most that channel's uncommitted posts and cursor update together, never a gap. `repair_missing_media(posts)` re-downloads media for posts whose files are no longer on disk — both the purged case and the failed-download case (`build_post_record` leaves `has_images=True` with no path), so the predicate has to special-case an empty `media_paths` rather than rely on `all()`. It runs inside `run_batch`'s existing `async with Scraper(...)` block, reusing the connected client and `channel_map`, fetches via `get_messages(entity, ids=[...])` in chunks of 100, skips a `None` (message deleted at Telegram), persists through `update_post_media_paths()` and is bounded by `MEDIA_REPAIR_MAX_PER_RUN` (200) — the first run after adopting the feature would otherwise turn a long-standing backlog of failed downloads into one enormous API burst. Per-channel failures are logged and skipped. `get_entity()` and the whole iteration are inside one try/except — a renamed/deleted channel or other error logs and returns whatever was collected so far instead of propagating; `run_batch` also wraps each `scrape_channel` call so one bad channel never aborts the rest of the batch.

**`analyzer.py`** — Uses the `openai` package against LM Studio's OpenAI-compatible REST endpoint (`/v1/chat/completions`), with a `timeout=120` client to bound a hung server. `SYSTEM_PROMPT` defines per-axis 1–5 scoring rubrics, category definitions, summary style (describe the event, never "the post"/"the image"; attribute unverified claims; use titles/offices exactly as the post gives them — never "corrected" from training knowledge, which once turned "President Trump" into "Former President Trump"), canonical entity rules (no news-agency/platform source credits), English translation of non-English text visible in images, and the threat-level rubric. `PostAnalysis` is a Pydantic schema with `title`, `summary`, four 1-5 score fields, `category`, `key_entities`, `image_description`, and `threat_level`. `threat_level` is validated by a `@field_validator` — anything outside `{CRITICAL, HIGH, MODERATE, LOW}` defaults to `MODERATE`. Structured output via `client.beta.chat.completions.parse(response_format=PostAnalysis)` with a plain text fallback (no `response_format` parameter — LM Studio only supports `json_schema` or `text`). Fallback response strips markdown fences before JSON parsing, then falls through to regex extraction. `_check_numeric_consistency()` is a wrapper over `_find_numeric_conflict()`, which returns the colliding (image, summary) number pair with ±30 chars of context so the drop log names what actually collided. Two numbers are only compared when they **count the same thing** — each carries the first `_NOUN_WINDOW_WORDS` (3) content words that follow it, singularised and stopword-filtered (`_nouns_after`), and the pair is skipped unless those sets intersect; a window rather than the next token alone, because "7.8 magnitude earthquake" has to meet "M8.4 earthquake". Without that test the check was a full cross-product whose 5% band is exact equality for small integers, so any image count collided with any similar-sized figure in the summary — and the prompt deliberately has the two texts describe different things. `_strip_non_quantity_numbers()` joins thousands separators and blanks times, years, `\d+-\d+` pairs (`Boeing 737-524`) and — via `_DESIGNATOR_RE`, an ordered alternation — every token mixing letters and digits (`T-72`, `Tu-22M3`, `Flightradar24`, `EP1048`, NOTAM `A0821/26`, `3rd`) **except** a letter-prefixed decimal, which is a real quantity (`M8.4` magnitude). Every substitution preserves length so offsets stay valid. `_NUM_RE` has no leading `\b` (it would skip the digit next to the letter in `M8.4`); that looseness is safe only because of the noun test — a digit pulled out of a name shares no noun and is never compared. Units of measure, currencies and magnitude words (`_UNIT_WORDS`) are excluded from the noun sets — a shared `km` or `usd` says how a number is expressed, not what it counts, and alone produced two of the three false positives measured on a live 500-post drain. **A mismatch is logged at WARNING and nothing is dropped**: the rule has one demonstrated true positive across 13,870 stored descriptions against a 3-for-3 live false-positive rate, and the remaining shape (1.4M current vs 2M projected barrels/day) shares both unit and noun, so no lexical test can separate it. `_existing_media(post, cap)` returns the first `cap` paths that are **still on disk** — the cap is applied after the existence filter, so a purged path no longer consumes one of the model's image slots, and `build_messages` / `build_batch_messages` / both token budgets all go through it. `_encode_image()`'s failure log is DEBUG, not WARNING: after that filter it means a file that exists but won't decode, not the routine retention case that once fired the line on every post of a historical backlog. **`_images_were_sent(post, cap)` gates the field entirely**: videos are never downloaded and a text-only post attaches nothing, so with no picture in front of it the model wrote what the post text implied — 53.5% of the 14,707 stored image descriptions were on posts with `has_images=0`, rendered by `generator.py` as observed Image lines. `_sanitize(analysis, images_sent=True)` now discards `image_description` and clears `image_substantive` when no image reached the model; `analyze_post()` passes the per-post value and `map_batch_results()` computes it per batch position, each with the cap that path actually attaches (`MAX_IMAGES_PER_POST` / `batch_images_per_post`). `_image_reject_reason()` is the single source of truth for why a description is unusable and `_sanitize()` logs which rule fired — the missing-description rate (15.4% of image posts) is dominated by those rejections and by the model omitting the field, not by the numeric check, which accounts for 0.6%. `_sanitize()` cleans title, entities, and image description (`_clean_image_insights` also rejects "none provided"/"no video provided" variants), blanks `title`/`summary` if they match `_REFUSAL_RE` (LLM meta-talk like "the user provided", "no content provided", "as an AI"), then HTML-escapes `title`, `summary`, `key_entities`, and `image_description` via `escape_html()` (utils.py) so LLM output can never inject markup into the rendered briefing. `analysis_to_record(post_id, analysis, model_used)` builds an `AnalysisRecord` from a `PostAnalysis` and is the single place both `process_unanalysed` (batch) and `run_daemon` (main.py) construct records, so fields like `title` can't diverge between the two paths again. `process_unanalysed(channel_map=None, since=None)` accepts an optional `since` cutoff (threaded from `--since`, see `main.py`) that scopes `get_unanalysed_posts()` to `timestamp >= since` and logs how many older stuck-unanalysed posts were excluded (still queued for a future unscoped run) — without `since`, behaviour is unchanged (every unanalysed post in the DB, regardless of age, is picked up). It first runs `_server_reachable()` — a 10s `models.list()` preflight probe — and aborts with everything left queued if LM Studio is down (a dead server fails in seconds, not hours). It then runs analyses concurrently up to `lmstudio.max_concurrent_analyses` and returns `(analysed_count, skipped_count)`; posts with `len(text.strip()) < MIN_CONTENT_CHARS` (30) and no *usable* media are skipped before calling the LLM, counted in `skipped_count`, and recorded with `category="Skipped"` (filtered out in `triage.py`) so they're never retried. "Usable" is `_has_usable_media(post)`: `has_video` (videos are never downloaded, so the flag counts on its own) or at least one `media_paths` entry that still exists on disk — `has_images`/`media_paths` record what was there at *scrape* time, but `main.purge_old_media()` deletes media older than `storage.retention_days` and `_encode_image()` drops the missing file silently, so without the file check a short post whose only content was a since-deleted photo was analysed blind and permanently marked analysed (measured: 92.3% of such posts got no `image_insights`, against a 22.7% baseline where the file survived). Those tombstones carry `summary="media unavailable"` to distinguish them from short-post skips. `process_unanalysed()` also accepts `limit` for bounded backlog drains. `analyze_post()` propagates its final error instead of fabricating an empty analysis — a failed post is logged, left unanalysed, and retried on the next run (the regex fallback is only used for received-but-unparseable responses). The analyzer's OpenAI client uses `max_retries=0` since `analyze_post` has its own `ANALYSIS_MAX_ATTEMPTS` (3) backoff loop (`RETRY_BACKOFF_BASE_SECS=10` × attempt number); other hoisted constants: `MAX_PROMPT_TEXT_CHARS=3000` (post text truncation before the prompt), `MAX_IMAGES_PER_POST=3`, `PREFLIGHT_TIMEOUT_SECS=10` (the `_server_reachable()` probe timeout). `max_tokens` on each analysis call is a **per-post dynamic budget** from `compute_token_budget(post, cfg.lmstudio)` — `min(analysis_base_tokens + text_chars*analysis_tokens_per_char + images*analysis_tokens_per_image, analysis_max_tokens)` (defaults 1500 + 0.3/char + 250/image, capped 4000), where text_chars/images are measured after `build_messages`' truncation/cap so unsent content never inflates the budget. This replaced the fixed `lmstudio.max_tokens: 800` (removed from config — a stale YAML carrying it fails loudly via `extra="forbid"`): reasoning models spend a large, mostly length-independent chunk of the completion deliberating before emitting JSON (observed `reasoning_tokens=797/800`, truncating the structured output), and LM Studio's OpenAI-compat endpoint exposes no reasoning-token controls, so the flat `analysis_base_tokens` carries that allowance. `analyze_post()` computes the budget once and passes it to both the structured and plain-text-fallback `_call_llm()` calls.

**Batched analysis (`analyzer.py`)** — several posts can share one LLM call, because the reasoning burn that dominates completion cost is largely per-*call*, not per-post (measured on `prism-ml/bonsai-27b`: 3,515 reasoning tokens for one text post vs 693/post in a batch of 10; 191 → 39.6 s/post). `BatchPostAnalysis` is a `PostAnalysis` carrying the post's 1-based `index`; `BatchAnalysis` wraps a list of them. `build_batch_messages(posts, system_prompt, cfg)` builds one multimodal user message where each `### POST n` text part is followed immediately by that post's images (capped at `batch_images_per_post`), with `BATCH_INSTRUCTIONS` appended to the system prompt telling the model the posts are unrelated. `plan_batches(posts, cfg)` groups text-only and media-bearing posts **separately** — images dominate the prompt and amortise far less (a 3-post image batch was only 1.6x faster than singles, against 4.8x for text) — and `_chunk()` closes a batch early when its prompt text would exceed `batch_max_prompt_chars`, so a run of long posts can't overflow context. `compute_batch_token_budget()` gives the call one flat `batch_base_tokens` reasoning allowance plus per-post/char/image increments, clamped at `batch_max_tokens`. `map_batch_results(batch, posts)` maps items onto batch positions **by their reported `index`, never by list position** (a dropped or reordered item would otherwise attach an analysis to the wrong post), dropping out-of-range and duplicate indices and running every item through the same `_sanitize()`. Indices alone are not enough, though: `google/gemma-3-4b` benchmarked at batch 10 dropped one post and **renumbered the rest densely 1..9**, so every index was unique and in range while 24 of 29 analyses described a different post — silent corruption that no positional check can catch. So each item also echoes `opening` (the first `BATCH_OPENING_WORDS`=6 words of the post it actually analysed) and `check_opening()` classifies it `match` / `mismatch` / `absent` against that post's own opening (word-overlap at `BATCH_OPENING_MATCH_RATIO`=0.5, so markdown and emoji prefixes don't cause false rejections). The three-way result matters: `mismatch` means the model attributed the analysis to the wrong post, `absent` only means the claim couldn't be checked — `prism-ml/bonsai-27b` returns no anchor yet attributes correctly, and reporting that as misattribution would condemn a model that merely ignores a field. Both non-matches are dropped and requeued (an unverifiable claim isn't a safe one) but they log differently. `salvage_batch_items(raw)` recovers the complete JSON objects from a response truncated at `max_tokens` — the posts they cover don't need re-analysing. `analyze_batch(posts)` returns `{position: PostAnalysis}` for whatever came back, `{}` if the call fails after `BATCH_MAX_ATTEMPTS` (2 — a failed batch has the per-post fallback, so it isn't retried for long). In `process_unanalysed()` the `MIN_CONTENT_CHARS` gate and the `since` filter both run **before** batching; posts from a channel with a `custom_prompt` stay on the per-post path (a shared batch call can only carry one system prompt); a batch of length 1 is routed to `analyze_post()`, so `batch_size: 1` (the default for both sizes) is bit-for-bit the pre-batching behaviour. When a batch returns fewer than `batch_min_yield_ratio` of its posts the missing ones are re-run individually (a mostly-failed batch signals something systematic); stragglers from an otherwise healthy batch are left unanalysed and retried next run, as before. `scripts/bench_analysis.py` (dev-only, needs a live LM Studio) benchmarks speed, coverage, alignment and **richness** — mean summary length, entity count and image-insight rate — across models × batch sizes on a seeded, cached sample. **Batching is off by default and should stay off unless the analysis model reasons.** Measured on `mistralai/ministral-3-3b` (zero reasoning tokens), a batch of 10 was only 1.7x faster on text and 1.07x on images while cutting mean summary length 281→179 chars and entities 3.6→2.3, with ~50% category agreement against the model's own single-post output — batching amortises per-call deliberation, and there is none to amortise. Single calls at `max_concurrent_analyses: 4` beat batch-10-sequential outright (1.10 vs 1.8 s/post on text). Everything above goes inert at `batch_size: 1`, so it costs nothing to leave in place for a future reasoning model.

**`models.py`** — `ModelManager`, a thin wrapper over the LM Studio Python SDK (`lmstudio`) used **only** to control which weights are resident; inference still goes over the OpenAI-compatible REST endpoint everywhere. It exists because the pipeline's two LLM stages want different models — analysis scores ~1,200 posts a day and wants a small fast non-reasoning VLM, synthesis runs once over the whole triaged day and is where reasoning earns its cost — and on a 16 GB card a 27B model (11.9 GB resident) leaves no room for a second one, so `model=` alone cannot switch stages. `ensure(key)` is a no-op when the key is already loaded (matched against both `identifier` and `modelKey`, since an LM Studio instance can be renamed); otherwise it unloads the other loaded LLMs (`unload_others`, default on — a failing unload is logged and the load proceeds) and calls `load_new_instance(key, config=..., ttl=model_ttl_seconds)`, the TTL being a safety net so a crashed run can't strand a model. The manager is **inert unless `manage_models` is set** (default off, so single-model setups are untouched) and **raises rather than degrading** when `manage_models` is on and the SDK can't reach LM Studio — a run that can't swap models is going to fail later anyway. `LMStudioConfig.model_for(stage)` resolves `analysis_model`/`synthesis_model` with a fallback to `model`; it is the single place that rule lives, so the analyzer and synthesiser can't drift. `analyzer.process_unanalysed()` and `synthesiser.run_analysis()` each `ensure()` their own stage's model at entry, which covers `--batch`, `--daemon` and standalone `--analyse` without `main.py` orchestrating anything; `analyses.model_used` records the analysis model that actually produced the row.

**`triage.py`** — Pure function `triage(pairs, config, channel_priorities, channel_credibilities) -> BriefingContent`. Posts with `analysis.category == "Skipped"` (see `analyzer.py` content gate) are excluded before scoring. Badge guard: a `CRITICAL` threat level with `category == "Rumor"` or `credibility_score <= 2` is demoted to `HIGH` at triage time (CRITICAL means "confirmed … underway"; this also stops unsubstantiated posts hijacking guaranteed lead slots, and applies to already-stored analyses). Composite score: `(0.4*importance + 0.3*urgency + 0.2*credibility + 0.1*relevance) × channel_priority × channel_credibility`, keyword-boosted (first match only, capped at 5.0), down-weighted by `rumor_penalty` when `category == "Rumor"`, multiplied by `threat_multipliers[threat_level]` (defaults CRITICAL 1.15 / HIGH 1.05 / MODERATE 1.0 / LOW 0.85, so badges nudge rank), then multiplied by a recency factor from `_recency_multiplier()` — an exponential half-life decay (`recency_half_life_hours`, default 24h) floored at `recency_floor` (default 0.7) so very old posts are demoted but never zeroed out. Recency is anchored to `min(now, end of the briefing day)` so retrospective runs (`--analyse --since <past date>`) reproduce the original day's ranking instead of decaying everything to the floor. After scoring, posts are clustered rather than dropped: `_find_duplicate()` matches on Jaccard word-overlap ≥ `dedup_jaccard_threshold` (default 0.28) on summary/title within `dedup_summary_window_secs` (default 6h), OR ≥`dedup_entity_overlap_count` (default 3) shared named entities within `dedup_window_secs`, OR ≥`dedup_entity_cluster_overlap_count` (default 4) shared entities within `entity_cluster_window_secs` — entity comparisons are normalised via `utils.normalize_entity()`, which lowercases and strips periods, then maps through `utils.entity_aliases()` (lru-cached, public since Phase 4 — `trends.py` also imports it directly instead of reaching into `triage`) so naming variants of the same actor match (e.g. "U.S." / "US" → "united states") — aliases are defined entirely in an optional gitignored `entity_aliases.yaml` at the project root (see `entity_aliases.yaml.example`); there are no built-in aliases, and normalization is a no-op without that file. `triage()` precomputes each `TriagedPost.norm_entities` (a `frozenset`) once before the dedup loop so `_find_duplicate()` never re-normalises the same post's entities per comparison; the dedup pass remains two separate loops over `kept` (summary/entity-overlap pass, then entity-cluster pass) rather than one merged loop, because a candidate that matches a *later* kept item on the first pass wins over an *earlier* kept item that would only match on the second pass — merging the loops would change that precedence (pinned by `test_dedup_cross_pass_ordering_prefers_summary_pass_over_earlier_cluster_match`). A matched duplicate is appended as a `CorroborationRef` (channel_slug, message_id, timestamp) on the higher-scored representative's `TriagedPost.corroborations` instead of being discarded. Representatives with corroborations get a multiplicative score boost — `score *= min(1 + corroboration_weight * n, corroboration_cap)` where `n` is the number of *distinct other channels* among the corroborations (same-channel reposts are merged but earn no boost; repeat posts from one other channel count once) — and the kept list is re-sorted afterwards since boosting can reorder items. `posts_clustered` (on `BriefingContent`) is the count of duplicates merged this way. Survivors split into `main_items` / `appendix_items` at `min_composite_score`; if fewer than `min_main_items` (default 15) clear the threshold, the highest-scoring appendix items are promoted to fill the shortfall, then `main_items` is capped at `max_main_items` (overflow goes to appendix). `BriefingContent` also carries `executive_items` (the Lead Reports) — all `CRITICAL`-threat-level items first (from main *and* appendix, so a low-scoring CRITICAL is still promoted), topped up with the highest-scored non-critical `main_items` to 10 total; criticals are never truncated, so the list grows past 10 when criticals alone exceed it. `executive_items` overlaps `main_items`/`appendix_items` by design (guaranteed-size constant `LEAD_SECTION_SIZE=10`) — the template de-duplicates at render time, while the synthesiser keeps consuming the full `main_items`. `channel_links` (slug → bare username) drives deep links and `category_counts` (category → post count) feeds the statistics table. `posts_scraped`/`posts_analysed`/`posts_skipped` are zero-valued by `triage()` and set externally by `main.generate_daily_briefing()`.

**`generator.py`** — `render_markdown(content)` resolves each executive (lead) item's `post.media_paths` to absolute paths (`Path(p).resolve()`) before rendering, then renders via Jinja2 (`templates/briefing.md.j2`); `generate_briefing(..., pdf=True)` then runs `markdown-pdf` (PyMuPDF backend) with `Section(md_text, root="/")` — the section root must be `/` because `fitz.Story` resolves image srcs against it and the default `"."` silently drops absolute paths (PDF shows an `[image]` placeholder instead). PDFs are saved to `{output_dir}/{YYYY-MM-DD}/TheDailyTelegram_{YYYY-MM-DD}_{HHMMSS}.pdf`; the `.md` source goes alongside it. Threat level badges are HTML `<span>` elements with inline `color:` styles (MuPDF renders text colour but not background-colour on inline elements). Images are emitted as `<img src="…" width="300">` tags, NOT markdown `![]()` + CSS `max-width` — `fitz.Story` ignores `max-width`, and a natural-size image landing at a page break makes Story silently drop that element *and the blocks after it* (this once swallowed an entire section). The template renders three *disjoint* tiers (computed via Jinja `reject('in', lead)` so no story prints twice): **Lead Reports** — `content.executive_items` in full detail (header, byline with channel/score/link, summary, entities, corroborations, video/image block, up to 3 embedded images); **Other Developments** — remaining `main_items` as compact `.dev-list` entries (badge, category, bold headline, channel/time/clamped-score/link meta, then the summary on its own line and a "Corroborated by N other channels" line with links when present); **In Brief** — remaining `appendix_items` in the two-column compact layout, with cross-channel corroboration abbreviated to a `+N corrob` marker in the score parens. There are no per-channel sections. Each lead item's corroborations split by channel: cross-channel refs render as "Corroborated by N other channel(s)" (N = distinct channels, deep links via `channel_links`), same-channel refs as a separate "Related posts from this channel" line with time-stamped links. The image/video block shows a "Video" line (with `▶ Watch on Telegram` link) when `item.post.has_video`, an "Image" line when `item.analysis.image_insights` is set, or nothing for text-only posts. Displayed per-item scores are clamped to 5.0 (the corroboration boost can push the internal composite above 5). Statistics render as a compact `.stats-block` div (Items with lead/other/in-brief split / Pipeline / Categories / Channels lines; the Pipeline line appears only when `posts_scraped`/`posts_analysed`/`posts_skipped` is non-zero, i.e. after a `--batch` run). The template ends with a static `.smallprint` "Reader's Key" explaining sections, scoring, dedup and threat levels — template boilerplate never touched by the LLM; its only dynamic value is the configured score threshold, interpolated from `content.min_composite_score` (set by `triage()` from config). CSS at `templates/briefing.css`.

**`synthesiser.py`** — Intelligence front page generator. `_triaged_to_dicts(main_items)` converts a list of `TriagedPost` objects into the dict format consumed by `synthesise()`, including `message_id` (used for source deep links). `synthesise(config, posts, trends=None, previous_intel=None)` calls LM Studio (temp=`SYNTHESIS_TEMPERATURE` (0.2), `max_tokens=lmstudio.synthesis_max_tokens` (config, default 24000) — reasoning models intermittently burn thousands of tokens on deliberation before emitting JSON, and a too-small budget surfaces as `finish_reason='length'` with truncated or empty content; the model has 32k context so the budget is deliberately generous — `timeout=SYNTHESIS_TIMEOUT_SECS` (300), no `response_format`) and strips markdown fences before parsing. The debug log of the raw LLM response (used for troubleshooting truncated/malformed synthesis output) is truncated to 2,000 chars — the full response can run to hundreds of KB. `_SYNTHESIS_SYSTEM`/`_SYNTHESIS_INSTRUCTIONS` instruct grounding (no invented events/numbers/actors, single-source claims marked unconfirmed), title/office fidelity (as the reports give them, not training knowledge), citation fidelity, themes as multi-report patterns, and canonical actor names (no news agencies/platforms); keep these prompts terse — verbose normative instructions made gemma-4-12b over-deliberate past its token budget. Each post is sent with a 1-based `index`; the prompt asks the model to cite supporting report indices as `"sources"` on each `key_themes`/`signals_and_warnings` item, and to set `"continuity"` (`new`/`confirmed`/`escalating`/`retired`) on each theme relative to `previous_intel["key_themes"]` if provided. `_format_trends(trends)` renders a "N-DAY MENTION TRENDS" block (entity + category prior→today counts, from `trends.py`) and `_format_previous_themes(previous_intel)` renders yesterday's themes for continuity — both return `""` when there's no data, and are appended to the user message before `_SYNTHESIS_INSTRUCTIONS`. `_validate_intel(data)` checks all four required keys, their sub-structure, and that each `key_themes`/`signals_and_warnings` item has a `"sources"` list. `_sanitize_intel()` HTML-escapes every text field via `escape_html()` (utils.py), filters `sources` to ints, and validates `continuity` against the four allowed values (defaulting to `"new"`). `_resolve_sources(items, posts, channel_links)` maps each item's `sources` indices (1-based, bounds-checked) back to `posts` entries, producing `source_links` (`channel_slug`, `time_str`, optional t.me `link`) for rendering. `_render_front_page_md(intel, date, posts=None, channel_links=None, emerging_entities=None)` renders `templates/intel_front_page.md.j2` — themes/signals show their `source_links` as footnotes and non-`"new"` `continuity` as an annotation; `emerging_entities` (entities mentioned today but absent from the prior 7 days, from `trends.py`) render as an "Emerging Actors / Topics" section (a single condensed `·`-separated line, `.emerging-list`) when non-empty. `_prepend_pdf()` uses `pypdf` to merge front page + briefing, writing to a temp file then atomically replacing the original with `os.replace()`; it is idempotent — it stores the front page's page count in the briefing PDF's `/IntelPages` metadata key, and on a subsequent call strips that many leading pages from the briefing before re-prepending, so re-running `--analyse` replaces rather than stacks the front page. `run_analysis(config, target_date, main_items=None)` is the async entry point — always opens the `Database` (closed via `try/finally`); when `main_items` is provided (passed from `run_batch`), synthesises directly from that triaged post list, when `main_items=None` (standalone `--analyse`) re-runs `get_days_posts_with_analyses()` + `triage()` to reconstruct the same post set as the main briefing. It then loads the last `trends.TREND_WINDOW_DAYS` (7) days via `get_posts_with_analyses_in_range()` to compute `trends` (`compute_trends()`), loads yesterday's `previous_intel` via `get_intel_assessment()`, calls `synthesise()`, and on success persists the result via `save_intel_assessment()` before rendering. Finds the latest `TheDailyTelegram_*.pdf` in the date dir, fails gracefully if LM Studio is unreachable, and never corrupts the existing PDF.

**`trends.py`** — Pure function `compute_trends(history, target_date) -> dict` over a multi-day list of `(PostRecord, AnalysisRecord)` pairs (typically the last `TREND_WINDOW_DAYS=7` days from `db.get_posts_with_analyses_in_range()`). Splits posts into "today" (`post.timestamp.date() == target_date`) vs "prior days" buckets, counting normalised entities (filtered through `utils.clean_entities`, then `utils.normalize_entity`) and categories in each; `category == "Skipped"` sentinel rows are excluded. Returns `entity_deltas`/`category_deltas` (`{"entity"|"category", "today_count", "prior_count"}`, sorted by today−prior descending, entities capped at `TOP_N_ENTITIES=10`) and `emerging_entities` — normalised entities with a non-zero today count and zero prior-day count, excluding `_EMERGING_STOPLIST` (newswire/photo credits and social platforms — sources, not actors) and entities starting with a digit (`_LEADING_DIGIT`: unit designators, years), sorted by today's frequency then alphabetically, capped at `MAX_EMERGING_ENTITIES=15`, and empty when there is no prior-day baseline at all (otherwise day one would flag everything). The template title-cases them for display.

**`utils.py`** — `connect_telegram_client(client, session_name)` is shared by `scraper.py` and `main.py`'s `run_daemon()` so both callers connect the same way: it calls `client.connect()`, turning a locked session file (`sqlite3.OperationalError`, e.g. daemon and batch run concurrently) into a `SystemExit` with an actionable message instead of a raw DB error, then falls into `client.start()`'s interactive login prompt only if `is_user_authorized()` is false (first run or an expired session). `escape_html(text)` escapes `&`, `<`, `>` (via `html.escape(text, quote=False)`) so LLM-derived text can't inject markup into the rendered Markdown/HTML output. `clean_entities()` and `_ENTITY_GARBAGE` filter junk/JSON-artifact entity strings (unchanged). `secure_file(path)` chmods a file to `0600`, used on the SQLite DB and Telethon `.session` files to keep credentials/data owner-only readable. `entity_aliases()` (lru-cached) and `normalize_entity()` — moved here from `triage.py` in Phase 4 since `trends.py` also needs them and importing a private name (`triage._normalize_entity`) across modules was a smell — load and apply the optional gitignored `entity_aliases.yaml`; behaviour is unchanged, `triage.py` and `trends.py` both import the public names now.

**`main.py`** — CLI entry point. `generate_daily_briefing(config, target_date, db, posts_scraped=0, posts_analysed=0, posts_skipped=0)` returns `(pdf_path, BriefingContent)`, setting those three counters on `content` after triage (the fourth, `posts_clustered`, is set inside `triage()` itself). `run_batch()` wires full scrape→analyse→triage→generate→synthesise pipeline, deriving `cutoff = since_dt or config.storage.analysis_cutoff(now)` and passing it as `process_unanalysed(..., since=cutoff)` — so plain `--batch` no longer sweeps the entire historical backlog, and calling `scraper.repair_missing_media(db.get_unanalysed_posts(since=cutoff))` inside the Scraper context before analysis; accumulating `total_scraped` across channels and unpacking `process_unanalysed()`'s `(analysed_count, skipped_count)`, then passes all three into `generate_daily_briefing()`; calls `run_analysis()` at the end, passing `content.main_items` so the Intel Assessment synthesises from the same triaged post set as the main briefing. All "today" values use `datetime.now(timezone.utc).date()` — the briefing day is always the UTC calendar date, regardless of host timezone. `--analyse` flag runs synthesis standalone (useful after `--generate`); accepts `--since` to target a specific date. `main()` caps `telegram.lookback_seconds` at the analysis window before the `--since` branch, so a cursor reset can't pull in history whose media will never exist; `--since` assigns `lookback_seconds` afterwards and therefore still overrides the cap deliberately. `--since TIME` flag (with `--batch`) resets all cursors and sets `lookback_seconds` in memory (accepts `HH:MM`, `YYYY-MM-DD`, `YYYY-MM-DDTHH:MM`), and the parsed `since_dt` is also passed through `run_batch(config, since_dt)` to `process_unanalysed(channel_map, since=since_dt)` so analysis is scoped to the same window as the re-scrape — plain `--batch` (no `--since`) analyses every unanalysed post **within the analysis window** (`storage.analysis_lookback_days`, default `retention_days`), as a catch-up safety net for posts left stuck by a prior LM Studio outage or analysis failure; anything older stays queued and is reachable only with an explicit `--since`, which is what keeps a months-old backlog out of every routine run. `run_daemon()` listens for live Telethon events (building each `PostRecord` via `scraper.build_post_record()`), **stores each post without analysing it**, and analyses newly stored posts in a periodic `_analysis_sweep()` task on a `DAEMON_ANALYSIS_INTERVAL_SECS` (600) cadence — the loop sleeps then runs, so sweeps can never overlap. Inline single-post analysis was removed because a reasoning model cannot keep up at this volume (bonsai-27b is 26–40 h/day of work for 1,100–1,700 posts one at a time, against ~7 h/day batched) and the old per-message tasks were unbounded. The sweep delegates to `analyzer.process_unanalysed()`, inheriting batching, the `MIN_CONTENT_CHARS` gate, the `_server_reachable()` preflight, the per-post fallback ladder and `ModelManager.ensure()` — the last of which closes a latent bug, since the old inline path never ensured its model and so fired at whatever the nightly synthesis had left loaded. The sweep passes `since=<daemon start time>`: unscoped it would sweep every unanalysed post ever stored (~92k in the live DB), and the daemon is documented as live-only with `--batch` owning historical catch-up. It runs `schedule_daily_generation()` as a background task with a `done_callback` that logs (`"Daily generation scheduler crashed"`, with traceback) if the task raises, so a scheduler crash is visible instead of silently vanishing. It also logs a `DEBUG` line per stored message (`"Stored post %s from %s"`) and runs an hourly heartbeat task (`HEARTBEAT_INTERVAL_SECS`, module-level so tests can shorten it) that logs `"Daemon heartbeat: %d posts stored, %d analysed in the last hour"` and resets its counters — so days of silent live operation are distinguishable from a dead listener; the heartbeat task has the same crash-visible `done_callback` pattern as the scheduler. `run_daemon()` calls `secure_file()` (utils.py) on the `.session` file after `connect_telegram_client()` to chmod it to `0600`. `schedule_daily_generation()` uses `generation.timezone` (IANA name, e.g. `"Europe/London"`) to interpret `generate_at` (the wall-clock trigger time), but the briefing date itself is computed via UTC `date()`; opens its own `Database` per iteration (closed via `try/finally`) and also calls `run_analysis()` after each nightly generation so the Intel Assessment is produced in daemon mode too. `purge_old_media()` removes date dirs older than `retention_days`. Config is only loaded after an action flag is confirmed (so `--help` works without a `config.yaml`).

## Data flow details

- **Idempotency**: `UNIQUE(channel_id, message_id)` in SQLite. Re-running the same window never duplicates records.
- **Cursor tracking**: `channel_cursors` table stores `last_seen_id` per channel. Scraper uses `offset_id=last_seen` on `iter_messages`. When cursor is 0, falls back to `offset_date` based on `lookback_seconds`. `--since` resets all cursors to 0 for a one-off historical lookback — do NOT use it for routine re-runs, as it forces Telegram to re-serve already-seen messages (wasted API quota). Plain `--batch` uses the cursor and only fetches new posts.
- **Daemon is live-only**: `run_daemon()` processes messages that arrive while running — it never backfills history. Always run `--batch` before switching to `--daemon` to catch up on historical posts.
- **Media**: Downloaded to `./data/media/<channel_slug>/<YYYY-MM-DD>/<message_id>.jpg`. Path constructed by `media_path_for()`.
- **`key_entities`**: Stored as JSON text in SQLite; deserialized back to `list[str]` in `get_days_posts_with_analyses`.
- **Output paths**: `briefings/YYYY-MM-DD/TheDailyTelegram_YYYY-MM-DD_HHMMSS.pdf` (unique per run) and `briefings/YYYY-MM-DD/briefing_YYYY-MM-DD.md` (overwritten on each run, stable name).
- **LM Studio compatibility**: Do not use `response_format={"type": "json_object"}` — this build only accepts `json_schema` or `text`. The structured output path uses `client.beta.chat.completions.parse()` with a Pydantic model; the fallback and synthesiser use plain `chat.completions.create()` with no `response_format` and parse the text response directly.

## Testing notes

- DB tests use `":memory:"` SQLite — the `db` fixture in `conftest.py` initialises schema fresh per test.
- `scraper.py` has no live-Telethon integration tests (requires credentials); `media_path_for()` is unit-tested and `scrape_channel`'s error-isolation / uncapped-iteration behaviour is covered with a monkeypatched client.
- `analyzer.py` tests construct `PostAnalysis` and message payloads locally (no LM Studio server needed). Full end-to-end runs against live Telegram/LM Studio are not covered by the suite.
- `asyncio_mode = "auto"` in `pyproject.toml` — async test functions work without decorators.
- 367 tests across 12 files; all pass with `pytest`.
- `ruff check src tests` (dev dependency) enforces import hygiene and unused-code discipline only (`select = ["F", "I"]`) — line-length/style rules are deliberately excluded to avoid a repo-wide reformatting sweep; see `pyproject.toml`.
- `scripts/audit_numeric_drops.py` and `scripts/drain_backlog.py` are dev-only, like `bench_analysis.py` — never imported by the package, never exercised by pytest. The audit replays `_find_numeric_conflict()` read-only (`mode=ro`) over stored analyses; it can only see rows that still *have* a description, so its count is a floor, not a measurement. `drain_backlog.py` reports the backlog split (media on disk / media purged with text / media purged without) and, with `--drain N`, analyses N posts scoped by `--since` to dates that still have media.
- Manual DB inspection uses Datasette via the optional `inspect` extra (`pip install -e ".[inspect]"`), configured by `scripts/datasette_metadata.yaml` — facets plus canned queries (joined analysed posts, per-channel threat mix, score distribution, richness by `model_used`, unanalysed backlog). It opens the DB `mode=ro` and rejects non-`SELECT` statements, so it is safe alongside a running `--batch`/`--daemon`; the metadata adds no views or schema. See the README's "Inspecting the database". Never run it with `--immutable` against the live DB — that asserts the file never changes and returns incorrect reads during a run. `scripts/datasette_plugins/shutdown_button.py` (loaded via `--plugins-dir`) adds a "Stop server" button that POSTs to `/-/shutdown` and raises `SIGINT` on Datasette's own process, so uvicorn exits gracefully and the terminal returns to a prompt; the route is POST-only, CSRF-checked, and refuses a non-loopback `Host`. It cannot reliably close the browser tab — browsers only let a page close a window a script opened — so it renders a "stopped, safe to close" panel instead. The `inspect` extra also pulls `datasette-media` (serves `data/media/` at `/-/media/photo/<post id>`, constrained by a SQL lookup against `posts.media_paths` so it can never serve an arbitrary file), `datasette-json-html` (inline thumbnails/links), `datasette-pretty-json` (the four JSON columns) and `datasette-vega` (charts); the `image_review` canned query pairs each thumbnail with the model's own `image_insights`. **`posts.channel_name` is the channel slug, not the Telegram username** — they differ for 7 of 16 channels — so t.me links must go through the `tme_link(slug, message_id)` SQL function registered by `scripts/datasette_plugins/channel_links.py`, which reuses `AppConfig.channel_link_map()` rather than duplicating the mapping. Datasette must be launched from the project root, since `media_paths` holds relative paths.

## Runtime requirements

- **LM Studio** must be running (local or remote) with a VLM loaded. Set `lmstudio.server_host` and `lmstudio.server_port` in `config.yaml`. If authentication is enabled, set `LM_API_TOKEN` in `.env`.
- **`.env`** is auto-loaded at startup via `python-dotenv`. Supported vars: `TG_API_ID`, `TG_API_HASH`, `LM_API_TOKEN`. These override the corresponding YAML fields.
- **Telegram session**: First run will prompt for a phone number/code; the session is persisted to `<session_name>.session` (gitignored).
- `config.yaml` is gitignored. Copy `config.yaml.example` and fill in `api_id` and `api_hash`.
